## 1. 阻塞级发现（先于一切设计）

### 1.1 🔴 BUG-1：工蚁依赖清单已缺失 4 个必需模块

`antnest_queen.py:201` 复制 16 个模块进工蚁隔离目录。实际仓库的 `antnest_*.py` 有 16 个，但**集合不同**：

**缺失（且工蚁启动必需）**：

| 缺失模块 | 被谁在模块顶层 import |
|----------|----------------------|
| `antnest_log.py` | `antnest_clone_worker.py:13`（模块顶层！） |
| `antnest_errors.py` | `code_tools.py:26`、`antnest_llm.py:15` |
| `antnest_config_schema.py` | `antnest_config.py:76`（工蚁必经） |

**当前为什么没炸**：本仓库是 editable 安装（`__editable__.antnest-1.3.1.pth`），site-packages 的 finder 把缺失模块从仓库根解析出来了。**这是开发环境的巧合，不是设计的性质。**

**炸了会怎样**：工蚁进程在 `antnest_config.py:25 → antnest_clone_worker.py:13` 处 `ModuleNotFoundError`，`result.json` 不生成，`antnest_queen.py:303-308` 返回 `{"status":"error","error":"工蚁未生成结果文件"}`。由于 `view_file`/`list_dir`/`grep_files`/`write_file`/`search_replace` **全部**经由 `spawn_clone`（`antnest_queen.py:502,513,532,546,565`），这是**整条工具链全瘫**。

**为什么 163 个测试抓不到**：`test_spawn_clone.py:84` mock 了 `Popen`；`test_spawn_clone_depth_block:66` 在深度闸门就 return 了。**仓库里没有任何一个测试真正启动过工蚁进程。**

> 这不是 v1.4 的风险，是**现在就存在的缺陷**。必须作为 Step 0 独立修复、独立提交，且先于一切 v1.4 工作。

### 1.2 🔴 BUG-2：安装包清单同样缺失 4 个模块

`installer/AntNest.iss` 缺 `antnest_log.py` / `antnest_errors.py` / `antnest_config_schema.py` / `antnest_ui_pure.py`。目前被 `launcher.ps1` 走 `uv run --project`（editable）掩盖。

**三份清单**（`antnest_queen.py:201`、`pyproject.toml:38-69`、`AntNest.iss`）必须由同一真源生成。这是 Module Inventory 存在的理由。

## 2. 架构约束（评审新增，不可违反）

### C1. `antnest_clone_worker.py` 必须是叶子模块

`antnest_config.py` 的 import 顺序是致命的：

```
antnest_config.py:25   import antnest_clone_worker   ← 先
antnest_config.py:33   import antnest_log             ← 后
antnest_config.py:47   antnest_clone_worker.run_if_clone_mode()  → sys.exit(0)
```

当 `antnest_clone_worker` 在第 25 行被 import 时，`antnest_config` 处于**半初始化**状态（只绑定了 ≤25 行的名字）。因此：

> **`antnest_clone_worker.py` 只允许 import `antnest_log` 与标准库。任何 import `antnest_config` 或传递依赖它的模块的行为都是循环导入，会让所有工蚁全瘫。**

v1 初版 R2 提出「把 `AN_PERM_LEVEL` 下发给工蚁、工蚁内自行判级」——如果按常规写法（`from antnest_config import PERMISSIONS`）实现，**会在第一次提交就炸掉整个工蚁群**。

**约束落地**：
- 工蚁侧权限**只读环境变量**（`os.environ.get("AN_PERM_LEVEL")`），不 import 任何 AntNest 业务模块
- 加测试：静态扫描 `antnest_clone_worker` 的传递 import，断言不触达 `antnest_config`

### C2. `ToolSpec.level` 是静态的，权限判定必须能读参数

`write_file` 的真实风险取决于**参数里的路径**（`_self_modification_gate(p)`，`antnest_queen.py:542`），`spawn_clone` 取决于**参数里的命令串**（`_command_self_source_target`，`:156`）。

如果 `check_tool("write_file", {"path": "antnest_config.py"})` 只看静态 `level=WRITE(1)`，在 `level>=1` 时会 **ALLOW** —— Agent 就能在无确认的情况下改写自己正在运行的源码。**这是 v1.4 会主动引入的安全回归。**

> **硬约束：参数敏感的判定结果必须覆盖静态 level 的 ALLOW。** 静态 level 只能用于「粗筛 + 工具是否可见」，不能作为最终放行依据。

### C3. 桥接是单向的，没有请求/响应通道

`AntNestCore.emit`（`antnest_bridge.py:715-720`）是 agent 线程 → 订阅者的单向调用。UI 侧所有「模态」都是 `app.run_js()` 单向展示。**不存在任何阻塞式提示通道。**

而 `send()` 在 `self.busy` 时返回 `("busy")`（`:1070`），`self.busy=True` 在新线程里设置（`:1083`），所以用户也无法通过输入路径应答。

> **v1 初版的「阻塞 ASK + 模态确认框」不可实现，本轮删除。**
>
> 权限询问复用**已验证的对话式授权协议**：`approval_required` → `break_loop` → 助手在聊天里说明 → 用户下一条消息授权（`_maybe_approve_self_modification`，`antnest_bridge.py:1050-1064`）。本轮只是把这个协议**泛化**到所有需要询问的权限场景，并补 `PERMISSION_REQUESTED/GRANTED` 事件。
>
> 真正的模态确认（`threading.Event` + 回复通道 + UI 线程泵）是独立课题，不许作为权限重构的副作用夹带。

### C4. `.antnest` 有歧义，写错地方 = 静默丢弃

`antnest_log.setup` 用 `os.getcwd()/.antnest`（`antnest_config.py:38-39`），`ANT_HOME` 用 `THIS_DIR/.antnest`（`:397`），`PROJECT_ANT_DIR` 用 `cwd/.antnest`（`:403`）。

`ANT_HOME` 在安装版指向安装目录（Program Files 下**只读**）。若把 events/checkpoints 放 `ANT_HOME`，**所有安装用户的记录会被静默丢弃**，而 fail-open 设计让失败不可见。

> **约束：events / checkpoints 一律落 `PROJECT_ANT_DIR`；fail-open 必须在首次写失败时打 WARNING。**

### C5. 消息列表没有稳定标识，且会被重绑定

`leave_memory_hints` 会**重建** messages 列表（`antnest_memory.py:78`：`[system, user] + kept`）。`antnest_bridge.py:1110` 用 `start = len(m.messages)` 记录的**索引**，在压缩后会指向另一个列表的中间位置。

> **约束：messages_tail / Plan / EventLog 都不能以列表索引为键。** checkpoint 存消息时以 `list(...)` 快照，写入前做结构修复（§5.3）。

## 4. Tool Registry（Step 2）

### 4.1 `antnest_registry.py`

```python
@dataclass(frozen=True)
class ToolSpec:
    name: str
    level: PermLevel          # 粗筛等级（C2：不能单独作为放行依据）
    schema_attr: str          # AntNest 壳上的 schema 变量名
    executor_attr: str        # AntNest 壳上的可执行函数名
    exposed: bool = True      # 是否暴露给蚁后 LLM

```

`TOOL_SPECS: tuple[ToolSpec, ...]` 是唯一硬编码清单。

**导入方向（无环）**：

### 4.3 MCP 建模（v1 初版错误）

v1 初版说「MCP 动态工具不进 TOOL_SPECS，但作为动态项追加到 `visible_specs`」。**这是错的**：`mcp_call(server, tool, args)` 是**单一派发器**（`antnest_queen.py:53`），`tool_executors` 里只有 `"mcp_call"` 一个键。追加动态项会产生**没有对应 executor 的 schema**，而 fail-closed 会把它们**全部拒绝**——MCP 从「能用」变成「全瘫」。

**修正**：MCP 就是**一个** spec（`mcp_call` + `mcp_list_tools`，level=`NETWORK`），外加运行时可用性检查（`MCP_ENABLED and MCP_HUB is not None`）。

**新增不变量测试**：`{s.name for s in visible_specs()} ⊆ set(tool_executors)`（反向不变量，初版遗漏）。

### 4.4 prompt 工具清单（v1 初版错误）

v1 初版要把工具列表改成 `{tool_catalog}` 运行时注入。**这会炸**：`SYSTEM_PROMPT.format(...)` 在 6 处被调用（`AntNest.py:163,234`、`antnest_bridge.py:813`、`antnest_memory.py:81`、`antnest_session.py:101`、`prototype_antnest.py:10780`），`str.format` 对未替换的 `{...}` 抛 `KeyError`；且工具可见性依赖运行时的 `MCP_ENABLED` / `COMPACT_PANIC`，import 期烘焙会**advertise 不存在的工具**。

**修正（低风险方案）**：不改 prompt 结构，改为**加一致性测试**——解析 `prompts/queen_system.md` 的工具列表，与 `TOOL_SPECS` 对比，不一致即 CI 失败。这样既消灭漂移，又不引入运行时风险。当前该测试会失败（`queen_system.md:33-49` 少列 3 个工具），**修 prompt 正是 Step 2 的一部分**。

### 4.5 畸形调用正则的覆盖变化

派生后的 `malformed_call_pattern()` 覆盖 **exposed** 集合 = 11 个；现手写正则（`antnest_loop.py:40`）是 13 个（多 `run_cli`/`run_python`/`leave_memory_hints`/`mcp_call`/`mcp_list_tools`）。

其中 **`leave_memory_hints` 丢失检测有实际风险**：该工具只在 `COMPACT_PANIC` 下暴露，模型若用纯文本伪造它的 JSON 调用，可能绕过压缩流程。

**修正**：`malformed_call_pattern()` 覆盖 **`TOOL_SPECS` 全集**（非 exposed），即 16 个，覆盖面严格大于现状。

## 5. 权限模型（Step 3）

### 5.1 等级与三态

```python
class PermLevel(IntEnum):
    READ = 0          # view_file / list_dir / grep_files
    WRITE = 1         # write_file / search_replace
    EXECUTE = 2       # spawn_clone / run_cli / run_python
    NETWORK = 3       # web_fetch / mcp_call
    SYSTEM = 4        # 危险命令模式命中 / 系统变更
    SELF_MOD = 5      # 写 AntNest 自身源码

class Action(str, Enum):
    ALLOW = "allow"; ASK = "ask"; DENY = "deny"
```

### 5.2 判定顺序（v1 初版顺序自相矛盾，已重写）

v1 初版按序判定，`level=5` 时规则 1 先命中 → `SELF_MOD <= 5` → **ALLOW**，导致「自源码永远需确认」这个不变量在最自然的配置下被绕过；且默认 `ask_above_level=3` 使规则 4 永不可达，三态退化成「二态 + 一个特例」。

**修正后的顺序（先特判，后分级）**：

```python
def decide(required, explicit_confirm, level, ask_above) -> Action:
    if tool_unknown:            return DENY    # fail-closed
    if explicit_confirm:        return ASK     # 自源码 / 危险命令 / L4，永不 ALLOW
    if required <= level:       return ALLOW
    if required > ask_above:    return DENY
    return ASK
```

- `explicit_confirm` 由 `check_command` / `check_write_path` 判定（自源码命中、危险模式命中、L4 系统操作）
- `ask_above` 默认 = `level`（即「未显式授予的一律询问」），需要严格降权时可显式调低
- `level=5` **不会**关闭自源码确认——`explicit_confirm` 在分级之前判定

### 5.3 删除两个语义冲突的配置项

| 删除项 | 原因 |
|--------|------|
| `allow_network` | 与 `level >= NETWORK` 重复，且规则表从不查询它 → 删，网络由 `level` 唯一控制 |
| `deny_write_outside_workspace` | `code_tools.resolve_path`（`code_tools.py:16-29`）**已经无条件**拦截越界路径。设 `true` 是 no-op，设 `false` 也无法放松 → 配置在说谎 |

### 5.4 配置

```json
"permissions": {
  "level": 3,
  "ask_above_level": 3,
  "audit": true,
  "checkpoint_enabled": true,
  "checkpoint_keep": 20
}
```

**`level=3` 是向后兼容的唯一正确取值**，逐项核对：

| 能力 | 现状 | level=3 判定 |
|------|------|-------------|
| 读文件 | 允许 | ALLOW (0<=3) |
| 写项目文件 | 允许 | ALLOW (1<=3) |
| 执行命令 | 允许 | ALLOW (2<=3) |
| web_fetch / MCP | 允许 | ALLOW (3<=3) |
| 危险命令（管理员） | 弹确认 | **ASK**（explicit_confirm） |
| 改自身源码 | 需明确同意 | **ASK**（explicit_confirm） |

**行为完全等价**，且 `level=0` 额外提供了「只读审阅模式」（v1 初版声称 `level=0` 是纯审阅，实际因 `ask_above_level=3` 会退化成「可一键授权的写与网」——已修正）。

### 5.5 危险模式表合并

现状三张表语义不同：`antnest_queen._DANGER_CLI_PATTERNS`（拦截）、`antnest_clone_worker.dangerous_patterns`（工蚁侧拦截）、`admin_utils.DANGEROUS_COMMANDS`（确认提示）。

**合并策略**：
- `_DANGER_CLI_PATTERNS` 升格为 `antnest_permissions.DANGER_PATTERNS`（唯一主表），吸收 `admin_utils` 的分类语义
- `admin_utils.DANGEROUS_COMMANDS` 保留（仅用于**展示**分类与风险等级，不做判定）
- **`antnest_clone_worker.dangerous_patterns` 保留不动**——它是工蚁进程内的第二道防线，且受 C1 约束不能 import 业务模块。这层冗余是正确的防御纵深

### 5.6 grant 生命周期（v1 初版缺失）

```python
class PermissionEngine:
    _once:  set[str]   # key = f"{level}:{scope}"，本回合有效
    _task:  set[str]   # 整个任务有效
    def grant_once(key) / grant_task(key) / reset_task()
```

- key 形如 `write:antnest_config.py`、`cmd:rm -rf /`，**按具体作用域授权，不按工具授权**
- 任务边界 = `TASK_COMPLETED` / `TASK_CANCELLED` 事件时 `reset_task()`
- 授权与拒绝都写 `audit.log`（`log_security_event` 接上）+ Event Log

### 5.7 D1 修复：`ALLOW_ALL_CLI` 声明但零读取

`antnest_bridge.py:809` 设 `ALLOW_ALL_CLI=True`，全仓库无任何读取点（`AntNest.py:211`、`antnest_config.py:292` 同）。实际后果：管理员模式下危险命令走 `admin_utils.get_user_confirmation()` → **阻塞式 `input()`**（`antnest_queen.py:166`），在 UI 里会**冻结工作线程**。

## 6. Plan DAG（Step 4）

### 6.1 数据结构

```python
class NodeStatus(str, Enum):
    PENDING = "pending"; RUNNING = "running"; COMPLETED = "completed"
    FAILED = "failed"; SKIPPED = "skipped"; BLOCKED = "blocked"

@dataclass
class PlanNode:
    id: str; title: str; detail: str = ""
    status: NodeStatus = PENDING
    depends_on: list[str]
    worker_ids: list[str]
    attempts: int = 0; error: str = ""; result_summary: str = ""
    started_at: float | None = None; finished_at: float | None = None
```

`Plan` 提供 `ready_nodes()`（依赖全 COMPLETED）、`progress()`、`to_dict()`、`to_prompt()`。

**环检测**：`update_plan` 与 `ready_nodes()` 都要检环；有环则拒绝更新并 `emit(PLAN_REJECTED)`，不让计划进入坏状态。

### 6.2 双数据源（`update_plan` + 自动派生）

1. **LLM 显式规划**：新增 `update_plan` 工具（`level=READ`，`mutating=False`——不改文件，只记录意图）
2. **自动派生（兜底，必须有）**：`spawn_clone` 被调用时，若无 RUNNING 节点且 LLM 从未调过 `update_plan`，自动开节点并认领该工蚁

第 2 条是**必需的**。flash 类模型经常不按格式调工具；只依赖 `update_plan` 会让 Plan 面板在多数真实任务里是空的，特性等于没做。

### 6.3 工蚁归属

`spawn_clone` 返回的 `task_id` 是执行侧真源。**`wrapped_spawn`（`antnest_bridge.py:896-928`）必须把 `wid` 写进返回结果**，否则 `plan.bind_worker(task_id, wid)` 无从建立映射。这是初版遗漏的接线点。

### 6.4 线程安全（初版遗漏）

`Plan` 被 agent 线程写、UI 线程读。`PlanNode` 是**多字段**读取（`status` + `result_summary` + `finished_at`），无锁会渲染出「✓ completed 但结果为空」。

> **约束：`plan` 与 `event_seq` 必须在同一个 `RLock` 临界区内变更**，事件 `seq` 在锁内分配。否则 UI 会观察到「有状态无事件」或「有事件无状态」，破坏「可重放」判据。

### 7.2 约束

- **线程安全 + 与 plan 同锁**（§6.4）
- **fail-open，但首次失败打 WARNING**（C4）
- **绝不记录 `reasoning_content`**（与 `antnest_runtime_state` 的既有约定一致）
- 参数截断沿用 `_safe_args`（>500 字符）
- 8MB + 3 代轮转

### 7.3 task_id 来源（初版遗漏）

需要**回合级 task id**。`task_manager` 的 `task_id` 是**工蚁级**的，不是回合级。

`antnest_events` 提供 `current_task_id()`，在 `AntNestCore._turn` 开头设置（模块全局 + `RLock`），`TASK_COMPLETED`/`CANCELLED` 时清空。未设置时事件落 `"adhoc"` 桶。

### 7.4 工蚁侧事件（明确推迟）

工蚁是**独立进程**，其事件需经 `AN_EVENT_FILE` 下发才能汇入。这会增加跨进程写入复杂度。

> **v1.4 只从父进程（蚁后侧）发 worker 生命周期事件**——蚁后本来就观察得到 spawn 的开始与结束。工蚁内部事件推迟到 v1.5。

### 7.5 与 `audit.log` 的分工（消除双写）

| 落点 | 内容 |
|------|------|
| `events/<task>.jsonl` | 任务生命周期 → **可重放** |
| `audit.log` | 仅安全事件（权限询问/放行/拒绝、危险拦截、配置变更）→ **可追责** |

`antnest_loop.py:150,160` 的 `log_tool_call/log_tool_result` 改由 `events.emit` 承担（方法保留不删，但循环不再调）。顺带接上闲置的 `AuditLogger.log_security_event`。

### 7.6 状态词汇表修正（初版遗漏）

`antnest_loop.py:154-159` 只把 `status in ("error","blocked","approval_required")` 视为非 ok。**新增的 `"denied"` 会被记成 `ok`**。必须加入非 ok 元组。

同理，`_DUP_CALL_LIMIT=3` 会在 3 次相同的**被拒**调用后触发「自我反思换方法」提示（`antnest_loop.py:131-141`）——等于在教模型换一个方式去重试一个刚被禁止的操作。**denied 结果不计入重复检测计数。**

## 8. Checkpoint / Resume（Step 6）

### 8.1 数据结构

```python
@dataclass
class Checkpoint:
    checkpoint_id: str; task_id: str; seq: int; created_at: float
    reason: str        # worker_done | plan_updated | user_stop | max_rounds | manual
    goal: str
    plan: dict
    messages_tail: list
    event_seq: int
    stats: dict
```

落 `.antnest/checkpoints/<task_id>/<seq>.json`（`PROJECT_ANT_DIR`），每任务 20 个 + 全局最近 5 个任务。

### 8.2 `rehydrate()` —— 不是切片（初版致命错误）

v1 初版写 `messages_tail: 最近 12 条`。**朴素切片会产出被 API 拒绝的消息列表**，且既有回填逻辑救不回来：

| 断裂 | 后果 |
|------|------|
| 切点落在工具批次中间 → 列表**以 `role:"tool"` 开头**，其父 assistant 已丢失 | OpenAI 兼容端点直接 400 |
| 既有回填（`antnest_loop.py:235-252`）只扫**最后**一个 assistant 且只补**缺失**响应、然后 `break` | 无法修复开头的孤儿 tool 消息 |
| 12 条几乎不含 `messages[0]`（system prompt：NEST.md / hints / ENV_INFO / 模型能力 / 深度规则 / 工具契约） | **安全与架构规则全部丢失** |
| `llm_chat_stream` 给 assistant 消息挂了 `reasoning_content`（`antnest_llm.py:254-255`） | §7.2 禁止记录思维链，但 §8.1 没对 `messages_tail` 施加同一条规则 → **思维链明文落盘** |

失败模式最恶劣：`ApiError` 被 `antnest_loop.py:269-275` 的宽 `except` 吞掉后 `break`，**整轮没有任何 assistant 消息**，UI 什么也收不到，判据「能恢复」静默失败。

**修正 —— `rehydrate(tail, system_msg) -> messages`**：

1. 前置**重新构建的** system 消息（不是切片里的）
2. 丢弃开头所有孤儿 `role:"tool"` 消息，直到遇到 `user` 或无 `tool_calls` 的 `assistant`
3. 对残留的 `assistant(tool_calls)`，**在该批次内**为未响应的 `tool_call_id` 合成 `{"role":"tool", content:"（工具调用被中断，未执行）"}`（复用 `antnest_loop.py:245-251` 的文案），**遍历全部批次而非只最后一个**
4. 写入前**剥离 `reasoning_content`**
5. 结果过一遍 `api_compat.sanitize_messages_for_api` 兜底

**测试**：构造一个工具批次被切断的 tail，断言 `rehydrate` 后无前导 `role:"tool"`，且过 `sanitize_messages_for_api` 后结构合法。

### 8.3 触发点与快照时机

触发：**每次工蚁归巢、每次 plan 更新、用户停止、达到最大轮次**。

但初版说「工蚁归巢时快照」是错的——那时 `agent_single_loop` 正在迭代 `msg["tool_calls"]`，下一步还会往 `messages` 追加，**快照是撕裂的**。

> **约束：在 `antnest_loop.py:55` 的 `while` 顶部（工具批次已闭合的静止点）取 `list(_A().messages)`，不从工具内部取。**

### 8.4 与 `stop_snapshot` 的双源（已知遗留 R5）

`antnest_runtime_state.record_stop` 保留不动（已被测试覆盖，`_runtime_prompt_context` 依赖它）。checkpoint 是超集，「用户停止」这一个点两者同时写。

> 这是**已知的一处双源**，v1.5 应把 `_runtime_prompt_context` 统一到 checkpoint store。本轮不碰已验证路径。

> **约束（本轮必修，因为 v1.4 会显著增加事件流量）**：
> 1. `send()` 在**启动线程之前**用 `try-acquire` 抢 `_turn_lock`，抢不到直接返回 `busy`
> 2. `sys.stdout` 恢复用比较交换：`if sys.stdout is mine: sys.stdout = old_out`
> 3. `on_core_event` 的 `CHATS`/`SUBTASKS`/`PLAN` 追加加锁
