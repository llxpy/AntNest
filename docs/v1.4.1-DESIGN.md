## 1. 反馈拆解

| # | 反馈 | 技术事实 |
|---|------|---------|
| 1 | 没有状态检测 | 顶栏胶囊仅反映 `status` 事件流（thinking/run/fail/idle），**不验证任何东西**：key 是否有效、目录是否可写、事件日志是否降级、工蚁依赖是否完整 |

## 2. 范围收敛：v1 砍掉的

| 砍掉 | 理由 |
|------|------|
| ⌘K 命令面板搜索 | 实测设置字段 **16 个**、6 个分区、每区 2–4 项，**没有滚动找不动的**（v1 写「超 25 个」是错的）。为 16 个静态键写一套搜索，代码量大于问题本身 |

保留 6 项：状态分区、分组卡片化、逐字段校验、脏状态、危险区、间距阶梯。

## 3. 捕获 `finish_reason`

### 3.1 为什么优先级最高

`finish_reason` 是把「模型返回空」细分化的**唯一**信息。缺它，截断 / 内容过滤 /
服务端资源不足全部塌缩成同一句话。

| finish_reason | 含义 | 该建议用户做什么 |
|---------------|------|-----------------|
| `length` / `max_tokens` | 撞 token 上限被截断 | 拆小任务 / 换大上下文模型 |
| `content_filter` | 被内容策略拦截 | 换措辞 |
| `insufficient_system_resource` | DeepSeek 侧资源不足 | 稍后重试 |
| `tool_calls` | 正常（只调工具没说话） | 无需处理 |
| `stop` / `end_turn` | 正常结束 | 若仍无正文 → 异常空回复 |
| 其他 / 缺失 | 未知 | 显式说「服务端未提供」 |

> v1 的表漏了 `end_turn` / `max_tokens` / `insufficient_system_resource`——
> 经 `api_compat.resolve_api_profile` 支持的 Anthropic-compat 端点会发这些值，
> 漏掉的都会落进 `empty_response`，正是本设计要消灭的那一类。

### 3.2 读点位置（E1，唯一硬约束）

```python
choices = chunk.get("choices", [])
if not choices:
    continue

# finish_reason 必须在此读取：终止块的 delta 为 {}，会被下面的
# `if not delta` 判空短路掉。放在其后则永远读不到，且测试会假绿。
_fr = choices[0].get("finish_reason")
if _fr:
    finish_reason = _fr

delta = choices[0].get("delta", {})
if not delta:
    continue
```

**「假绿」是这里的主要风险**：任何在 `:193` 之后读 `finish_reason` 的实现，
配套测试全部通过却零覆盖——因为代码路径根本不可达。测试必须用真实 SSE 字节流驱动
（§8.1）。

### 3.3 传递方式（E2）

**不用模块级全局。** 三个理由：

1. `agent_single_loop` 最多 60 轮，每轮覆盖一次 → 末尾只读得到**最后一轮**的值，
   而正常多轮回合的最后一轮几乎必然是 `tool_calls` 或 `stop`，规则 5/6 永不触发。
2. 函数不返回值（`:479` 是裸 `break`），v1 说的「每轮读一次存进局部变量交给诊断层」
   **不存在这条通路**。
3. 模块全局在回合重叠时串写。`antnest_bridge.py:1153` 的 `_turn_lock` 只是
   「大体」防住了重叠，不是保证。

改为：

```python
# antnest_llm.py
return message, usage, finish_reason     # 3 元组

# antnest_loop.py
class LoopResult:
    outcome: str            # replied / empty / max_rounds / denied / approval / cancelled
    rounds: int
    finish_reasons: list[str]      # 逐轮，诊断用「哪一轮截断的」
    retry_notes: list[str]         # 空回复/畸形调用等重试告警原文（§4.5）
    last_tool_statuses: list[tuple[str, str]]   # (tool, status)
```

`agent_single_loop` 从 `return` 改为 `return LoopResult(...)`，各 `break` 点填对应
`outcome`。

**双命名空间说明（§9 AGENTS.md）**：`AntNest.py:66` 是 `from antnest_llm import *`，
`import *` **跳过下划线前缀名**，所以下划线私有名天然只存在于子模块命名空间。
这里改用返回值，不再有跨命名空间的全局状态需要同步——这正是选返回值的原因。

### 3.4 不做 `_stream_emit("finish_reason", ...)`

`prototype_antnest.py:4273-4501` 的 `stream` 处理器是**无 else 的 if/elif 链**
（覆盖 `start/reasoning_start/reasoning/reasoning_end/content/end/interrupted/usage`）。
新增 phase 会被静默丢弃。v1 说「UI 侧记录」其实是死代码。
本轮不 emit；`LoopResult` 已带全部信息，UI 不需要第二通路。

## 4. 回合失败归因

### 4.1 形态：纯函数

```python
def diagnose_turn(result: LoopResult, *, cancel: bool, exc: BaseException | None,
                  token_cap: int) -> TurnDiagnosis | None
```

**纯函数、单一入参、返回 dataclass。** 这样 4 条规则就是 4 个 dict 分支，
全部可测；调用点只有 `antnest_bridge._turn` 一处。

### 4.2 只保留可达规则（E3）

v1 列了 10 条，逐条核对 `antnest_loop` 实际行为后，**7 条永不可达**：

| v1 规则 | 为何不可达 |
|---------|-----------|
| `permission_denied` / `awaiting_approval` | 分支会 append **非空** assistant 文本（`:425-467`），`reply_text` 非空，收尾处不进入空回复路径 |
| `max_rounds` | 空回复被就地重试（`:204-212`），直到有文本或 `_rounds > 60` → 规则 4 总是**抢先**，遮蔽 5/6 |
| `reasoning_only` | 同上，该消息被 `pop()` 后重试，不存活到收尾 |
| `tool_failed_only` | 工具错误回喂模型（`:331-336`），模型重试，回合以文本结束 |

v2 实际规则（4 条，判据全部来自 `LoopResult`）：

| # | code | 判据 | 展示 |
|---|------|------|------|
| 1 | `cancelled` | `cancel` | 保留现状（已单独处理） |
| 2 | `error` | `exc` 非空 | 异常类 + 错误码 + 首行（§4.5） |
| 3 | `empty_response` | `outcome == "empty"` | **逐轮**列出 `finish_reasons`，定位到具体哪一轮开始异常 |
| 4 | `token_budget` | `usage.total > 0 and usage.total >= token_cap` | 上下文已满 |

> 规则 4 必须门控 `total > 0`：`antnest_llm.py:63-64` 只对
> `deepseek/openai/openai_compat` 请求 `stream_options.include_usage`，
> MiniMax/Kimi 拿不到 usage 会回落成全 0（`:263-264`）；`antnest_loop.py:322-323`
> 在 `leave_memory_hints` 后也会清零。不门控则对半数 provider 误报。

### 4.3 展示形态

```
现在：（本轮没有文本回复，详见运行日志）

之后：本轮没有产生回复。
      模型在第 3 轮返回了空内容（finish_reason=length），
      重试 2 次后仍未产生正文。本轮共消耗 128000 / 128000 token。

      可以尝试：
        · 把任务拆小，或分几轮做
        · 在设置里换一个上下文更大的模型
        · 归档旧会话以释放上下文
```

**逐轮列出 `finish_reasons`** 是关键：它把「某一轮被截断」和「一直就没输出」
区分开——前者拆任务有用，后者是提示词/模型问题。

### 4.4 事件查询（E6）

不新增规则，因此不需要「本轮事件」查询。若后续要展示权限/工具事件，用
turn 开始时 `_events.emit(TASK_CREATED)` 返回的 `EventRecord.seq` 作水位，
配合 `tail()`（内存环，`RING_MAX=500`）过滤——O(500) 不落盘。
`current_task_id()` 在收尾处仍有效（`finally` 才清空）。

### 4.5 两处零成本现成收益

- **空回复重试告警**：`antnest_loop.py:204-212` 已经把「回复为空，没有输出也没有
  调用工具，请重新回答」喂给模型，并 `pop()` 掉空消息。**这条诊断是模型自己算出来的，
  现在被丢弃。** 收进 `LoopResult.retry_notes` 并展示，约 3 行。
- **异常类 + 错误码**：`_turn` 异常分支已把 `traceback` 写进 `ui_trace.log`，
  但气泡里只有 `str(e)`。`antnest_errors.AntNestError.default_code`（如 `LLM-001`）
  没进 UI。补进气泡约 5 行，直接回答「为什么失败」。

## 5. 诊断层 `antnest_diag.py`

### 5.1 挂在哪（修正 v1）

**不复用 `status_text()`**——它无人调用，是死代码。新增
`AntNestCore.health()` 供 UI 拉取；胶囊状态由 `health()` 的最差项决定，
`_set_pill()` 消费之。

### 5.2 依赖注入（评审 MAJOR-7）

`antnest_diag` 若直接读全局会遇到：① 与调用方 `antnest_bridge` 循环依赖
（`CORE_CFG`/`UI_CFG`/`verify_api`/`list_skills` 都在 bridge 里）；
② `antnest_events.get_log()` 是**可变单例**（`:482-488`），在
`antnest_config` 初始化前调用会用 `os.getcwd()/.antnest` 建错实例，
下一次正确调用还会**替换**它；③ `PROJECT_ANT_DIR` 在 import 期冻结
（`antnest_config.py:404-405`），evals chdir 后会读错目录。

故显式注入：

```python
@dataclass
class DiagContext:
    core_cfg: dict; paths: dict[str, str]; perm_level: int | None
    cap_summary: object; events_enabled: bool; events_degraded: bool
    verify: Callable[[], tuple]        # 昂贵，由 bridge 注入
    list_skills: Callable[[], list]    # 昂贵，由 bridge 注入
    inventory_missing: frozenset       # 启动时算好，注入
```

**所有检查项是 `DiagContext` 的纯函数**——这也是它们可测的唯一方式。

### 5.3 检查项

廉价（打开面板即跑，硬预算 <50ms）：

| key | 检查 | fix 文案示例 |
|-----|------|------------|
| `api_config` | base_url 格式 / model 非空 / key 存在 | 「未配置 API Key」 |
| `config_parse` | 原始读 `config.json`（**不能走 `bridge._read_json`**，它 fail-soft 吞异常返回默认值，检测不到损坏） | 「第 N 行不是合法 JSON」 |
| `dirs` | 三目录存在且可写 | 「`<path>` 不可写，检查权限或磁盘」 |
| `disk` | `disk_usage` 剩余空间（**不报占用**，§2） | 「剩余不足 500MB，事件与检查点会写失败」 |
| `event_log` | 读 `antnest_config.EVENT_LOG` 的 degraded；**区分「用户关的」与「降级了」** | 「事件日志已降级，重放不可用」 |
| `permission` | level + 是否偏离默认 3；`PERMISSION_ENGINE` 为 `None` 时报未知 | 「当前 L0 只读，写操作会被拒绝」 |
| `model_cap` | `_CAP_SUMMARY` **三态**：str 占位 / dict 校准后 / 缺失（`antnest_config.py:277,293`） | 「已跳过 /models 检测，用默认上限」 |
| `mcp` | 启用状态 + 服务器数 | 「已启用但 mcp.json 不存在」 |
| `clone_pool` | 残留工蚁目录（只 `listdir`，不递归） | 「N 个残留目录，可清理」 |

昂贵（仅「深度检测」显式触发，缓存 60s）：`api_reachable`（注入 `verify`）、
`skills`（注入 `list_skills`）、`inventory`（见下）。

`inventory` 不在廉价桶：437ms 是预算的 8.7 倍（E5）。启动时算一次注入
`inventory_missing`，判据**只断言 `missing` 半边**——干净树上
`antnest_launcher.py` 属预期 extra（`_NON_RUNTIME`），断言全等会永久 WARN。

### 5.4 硬约束

- **fail-soft**：每项 try/except 转 `Check(level=ERROR)`；`health()` 最外层再兜一层。
  诊断本身绝不能把 UI 搞崩（Step 4 事件日志约束的延续）。
- **不回显凭据**：只报「已配置/未配置」+ **长度桶**（`>32` 字符），不报尾 4/6 位。
  短 key 的尾段是密钥的显著比例。`effective_config()` 现返回 `key_tail` 6 位
  （`antnest_bridge.py:1518-1530`），新代码不沿用。
- 无网络项不加 poller，**不做后台轮询**。

## 6. UI 改造

### 6.1 修按钮 bug（先做，1 行 CSS）

真因（E-misdiagnosis）：`app.css:386-388` 使 `.monitor-panels .card.panel` 成为
列向 flex 容器，`<button>`（`prototype_antnest.py:13595`）被默认
`align-items:stretch` 拉满宽。`.btn-expand` / `.btn-mini` **都是零规则死类**。

```css
.plan-card > .btn{ align-self:flex-start; }
```

**加测试断言 CSS 里确有该规则**——沿用 `tests/test_ui_plan_render.py:251` 的
`assertIn(cls, css)` 约定。死类能发出去正是因为没人断言它存在。

### 6.2 状态面板

```
现在：蚁后 [● 就绪]              ← 仅 status 事件流

之后：蚁后 [● 就绪]              ← 9 项廉价检查聚合，颜色取最差项
     点开 →
       ✓ API 配置    deepseek-v4-flash · 上限 128k
       ✓ 目录可写    .antnest
       ⚠ 权限档位    当前 L3（默认）

```

`✓ API 配置 deepseek-v4-flash · 上限 128k` 这一行**今天已经存在**
（`antnest_bridge.py:805`）——**v1 的 mockup 把已有输出当成新产出**。

### 6.3 设置页现代化（6 项）

| # | 改动 | 依赖 |
|---|------|------|
| 1 | 顶部「系统状态」分区（9 项检查 + 深度检测） | §5 |

## 7. 实施顺序

## 8. 测试可行性（诚实版）

评审指出 v1 的「逐项截图验证」是不可执行的验收标准。实际情况：

| 范围 | 可测性 | 手段 |
|------|-------|------|
| §3 `finish_reason` | 可测 | **需新建 SSE 字节流 fixture**——现无任何测试驱动 `llm_chat_stream`。AGENTS.md H3 点名的正是这类历史空白。这是本轮最高价值的测试 |
| §4 `diagnose_turn` | 可测 | 纯函数，直接构造 `LoopResult` |
| §5 `antnest_diag` | 可测 | 纯函数 + `DiagContext` 注入（若无注入则只能 mock） |
| §6.1 按钮 | 可测 | `assertIn` CSS 规则（`test_ui_plan_render.py:251` 同款） |
| §6.3 设置 2/3/6 | 可测 | CSS/HTML 字符串断言（`test_ui_wiring.py:288-302` 同款）。**仅证明存在，不证明行为** |
| §6.3 设置 1/4/5、§6.2 面板交互 | **不可测** | JS/CSS 行为，Python 测试无法覆盖。走浏览器后端（`phtmlwin.py:470,588`，`test_phtmlwin_window.py:78-89` 已有）人工过一遍 |

**开发回路成本**（评审 MAJOR-13）：`load_js()`/`load_css()`
（`ui_assets_loader.py:27-32`）各只调一次并**内联进 HTML**
（`prototype_antnest.py:12880`、`:2212`），无 `<script src>`，无 dev-reload 通路；
`_reload()` 只重导入 Python 核心、不重渲染。**每改一次 JS/CSS 都要重启整个进程**，
而 `prototype_antnest.py` 有 13,700 行。

> **决定**：本轮**不**新增 dev-reload（会引入 v1.4 未预见的打包/缓存风险）。
> 改为**把 §6.3 零 JS 的 2/3/6 提前到步骤 5**，让大部分视觉改动在一次重启内完成。
> 步骤 6 的 JS 部分按 1 次重启 = 1 个批次规划。§8 列为遗留 R10。
