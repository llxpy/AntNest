## 0. v2 修订说明

v1 的整个设计建立在一条「已验证的静默死亡链」上。评审逐环核对后，**第 1-2 环是错的**，
而我的验证方法本身有缺陷。

### 0.1 前提被推翻

v1 声称：`prototype_antnest.py:1142` 的模块级 `import antnest_bridge`
→ 传递到 `antnest_config` → import 期 `sys.exit(1)` → 静默死亡。

**事实**（`antnest_bridge.py:45-48`）：模块级只 import
`api_compat` / `antnest_runtime_state` / `antnest_events` / `memory_tree`，
**没有一个到达 `antnest_config`**。`antnest_config` 只经
`antnest_bridge.py:775` 的**惰性** `importlib.import_module("AntNest")` 到达，
而那里有 `except SystemExit`（`:776`），且 `sys.stdout/sys.stderr` 已在
`:772` 被换进 `cap`——所以错误原文被完整捕获。`antnest_bridge.py:1192`
把它渲染成聊天消息：

> `核心未就绪，无法执行。` + `未配置 API Key。请在 config.json 中设置 api_key…` + `配置文件位置：…`

**今天的行为是**：窗口打开 → 用户输入 → 得到具体且可操作的中文错误。
`launcher.ps1:99` 的 `WaitForExit()` 永不返回。**G1 在这条路径上已经满足。**

### 0.2 我的验证方法错在哪

我写了 `_probe_systemexit.py` 证明「`SystemExit` 不经 `sys.excepthook`」，
然后把它当成了「AntNest 的进程会静默退出」。

这是**关于 CPython 的事实，不是关于 AntNest 的事实**。探针里的 `sys.exit(1)`
是探针自己写的，我从未验证 AntNest 的 `SystemExit` 能到进程顶层。
AGENTS.md §1 把 R8 记为「历史版本在 401 时退出进程，已修复」——
但真正让 R8 不再致命的是**惰性 import + `except SystemExit`**，而我只读了 §1 的
结论，没读 `antnest_bridge.py:752-789` 的实现。

> **教训**：声称「已验证 N 环链路」时，必须逐环给出 file:line，
> 并区分「事实成立」与「我推断它成立」。这里我用一条对的事实
> 推出了一条假的事实。

### 0.3 P6 从「核心」降级为「删除」

v1 的 P6（预检 API Key，未配则中止）**会造成净倒退**：

- 预检拦下 → 应用不启动 → **设置页打不开** → 而
  `antnest_bridge.py:846-860` 的 `apply_settings` 热应用 key
  正是唯一的自助修复路径。
- v1 §3.4 还建议弹窗文案写「打开设置 → 模型连接」——**推荐了一条被自己挡死的路**。

结论：**P6 删除**。R8 的表现已经可观测，不需要在 PowerShell 里重写一遍。

### 0.4 v1 另外三处会引入新问题

| # | v1 写法 | 问题 | 证据 |
|---|---------|------|------|
| R1 | `Start-Process -RedirectStandardOutput/Error` 记日志 | `-RedirectStandard*` 强制 `UseShellExecute=false`，而 `WindowStyle` 仅在 `UseShellExecute=true` 时生效。父进程是 ps2exe `-noConsole`（无控制台）→ **控制台子进程会新分配一个可见控制台**。直接破坏 `launcher.ps1:94-97` 写明的「零黑框」硬约束 | .NET `ProcessStartInfo` 文档语义 + 评审 winexe 实测 |
| R2 | `$p.WaitForExit($TimeoutMs)` + 超时提示 | 正常应用一直运行到用户关窗，**每一次成功启动都会超时**。且 v1 §3.3「有限等待」与 §3.3「保留常驻语义」自相矛盾 | 设计内部矛盾 + 逻辑必然 |
| R3 | 「改 `AntNest.iss:91-92`」 | **`:91` 是 `launcher.ps1`，`:92` 是 `install_deps.ps1`**（被 `:118` 的 `[Run]` 调用装 uv 与预建 venv）。按 v1 改会删掉安装期依赖脚本 | `AntNest.iss:91-92` |
| R4 | 测试 T1/T3/T8 | T1「函数名集合一致」被 v1 自己的 `Show-Error`/日志/key 解析器要求否证；T3 `all(ord(c)<128)` 否证 v1 §3.4 自己要求的中文字面量；T8 禁止文件存在，与 §3.5 的逃生口冲突 | 设计内部矛盾 |

### 0.5 修正后真正剩下的问题

评审把前提推翻之后，**有一批问题是真的**（v1 没看见，v2 保留）：

1. **没有顶层错误陷阱。** `launcher.ps1:11` 是 `$ErrorActionPreference="Stop"`，
   **整份脚本没有 try/catch**。`-noConsole` 下没有控制台，任何未处理的
   终止性错误都不可见。未设防的抛出点：
   - `launcher.ps1:12` `Add-Type -AssemblyName System.Windows.Forms`
   - `launcher.ps1:53` `irm … | iex`（有 try，但 `irm` 本身可能在 `$ErrorActionPreference=Stop` 下抛出）
   - `launcher.ps1:86` / `:96` `Start-Process`（AV 隔离 `uv.exe` 时抛）
   - `Show-Error` 的 `catch {}`（`:17`）吞掉自身失败 → 无错误路径
2. **不检查子进程退出码。** `:99` 的 `WaitForExit()` 之后直接结束脚本。
   `uv run` 同步 venv 失败、离线首启、`pywebview` import 失败、venv 损坏
   —— 这些都会让 python 退出非零，而用户看到的仍然是什么都没有。
   **这才是真正的静默失败面。**
3. **WebView2 探测每次启动都重扫。** `:64-81` 的 `Get-ChildItem -Recurse`
   在 `EdgeWebView\Application` 上每次双击都跑一遍，无 marker 缓存。
   而 Edge Update 维护的 3 个注册表键只需 ~1ms。
4. **`$app` 推导有陷阱。** `:22-23` 用 `MainModule.FileName`，
   未编译运行时它等于 `powershell.exe` → `$app = System32` → 预检会
   报「安装不完整」并指向 `C:\Windows\System32`。
5. **死代码。** `launch.ps1` 是 `launcher.ps1` 的近似复制品，无任何消费者
   （`AntNest.iss:89` 只打包，快捷方式全指 `AntNest.exe`），
   却是最像真相的一份，后来者会本能地去改它。

替换 `launcher.ps1`。`build_launcher.ps1:25` 的 `$input` 改指它。

### 3.1 顶层错误陷阱（G1，最高价值，2 行）

```powershell
try   { Start-AntNest }
catch {
    Write-BootLog ("FATAL: " + $_.Exception.Message)
    Show-Error ("AntNest 启动失败：`n" + $_.Exception.Message +
                "`n`n日志：" + $logFile)
}
```

覆盖 §0.5-1 列出的全部未设防抛出点。`Show-Error` 自身失败时
（WinForms 不可用）**降级为只写日志**，不再 `catch {}` 静默 `exit 1`
（`launcher.ps1:17` 现在的行为就是吞掉）。

### 3.2 预检闸门（G1，只允许「修好或说清」）

| # | 检查 | 失败处理 | 是否阻止启动 |
|---|------|---------|-------------|
| P1 | 安装完整性：`prototype_antnest.py` + `pyproject.toml` + `antnest_bridge.py` | 弹窗 + **列出缺哪个** + 「请重装」 | ✅ 阻止（应用本来必失败） |
| P2 | 日志目录可建可写 | 降级为内存日志 + 弹窗说明「日志将不可用」 | ❌ 不阻止 |
| P3 | uv 定位 | 缺失则安装；装不上 → 弹窗 + 官方地址 | ✅ 阻止（无 uv 跑不了） |
| P4 | WebView2（**注册表优先**） | 缺失则安装；装不上 → 弹窗 + 官方地址 + 说明 UI 需要它 | ❌ 不阻止（应用自己会报更准） |
| P5 | 磁盘剩余空间 | < 500MB → 警告（首次建 venv 会失败） | ❌ 不阻止 |

**P1/P3 阻止启动是合理的**：这两种情况下应用 100% 起不来，
拦住只是把「无声失败」变成「有因可循」，不损失任何自助修复路径。

**P4 不阻止**：WebView2 缺失时 python 会自己给出更准确的错误
（`phtmlwin` 的回退路径与报错），在 PowerShell 里复现只会更差。
本轮只把探测顺序改成注册表优先（省掉每次启动的递归扫描）。

**删掉的 P6（原 API Key 预检）**：见 §0.3。

### 3.3 启动：保持现状机制（G4）

```powershell
$p = Start-Process -FilePath $uv `
     -ArgumentList "run","--project",$app,"python",$entry `
     -WorkingDirectory $app -PassThru -WindowStyle Hidden
$p.WaitForExit()          # 无限等待：exe 作为父进程常驻（G4 不变）
$code = $p.ExitCode
if ($code -ne 0) { Report-ChildFailure $code }
```

- **不使用 `-RedirectStandard*`**（G4 / §0.4-R1）。
- **不使用超时**（G4 / §0.4-R2）。健康应用就是长时间运行，
  任何超时都会在每次成功启动时误报。
- 父进程不做 job object，脚本返回后子进程存活——这正是我们要的
  （窗口关了 exe 才退出）。

### 3.4 失败汇报（G2）：读应用自己的日志

子进程非零退出时，**读已经在写的那份日志**，不捕获子进程 stdout：

| 日志 | 位置 | 作用 |
|------|------|------|
| `antnest.log` | `%LOCALAPPDATA%\AntNest\.antnest\antnest.log`（`antnest_log.py:276-285`） | 应用自己的结构化日志，**已含 R8 的完整原文与配置路径** |
| `ui_trace.log` | `%LOCALAPPDATA%\AntNest\.antnest\ui_trace.log`（`antnest_bridge.py:55-56`） | 启动阶段 S0-S7 追踪 |
| `boot.log` | `%LOCALAPPDATA%\AntNest\logs\startup.log`（**本入口新写**） | 入口自身的动作：预检结果、uv 路径、退出码 |

弹窗内容：

```
AntNest 未能启动（退出码 1）

应用日志最后 12 行：
  …（原文）…

日志位置：
  %LOCALAPPDATA%\AntNest\.antnest\antnest.log
  %LOCALAPPDATA%\AntNest\logs\startup.log
```

> **这是 v1 → v2 最重要的修正**：不重定向、不新增捕获机制，
> 而是读应用**本来就在写**的日志。信息更全、零新增失败面。
> `install_deps.ps1:33` 已在安装期证明依赖可离线装上；
> `antnest.log` 已含 R8 原文。诊断能力已经存在，只是没人读。

### 3.5 `$app` 推导修正（§0.5-4）

```powershell
$exePath = [System.Diagnostics.Process]::GetCurrentProcess().MainModule.FileName
$app = Split-Path -Parent $exePath
# 未编译运行时 MainModule 是 powershell.exe，$app 会变成 System32。
# 优先用脚本自身目录：编译后的 exe 其目录即 $app，语义一致。
if ($PSScriptRoot -and (Test-Path (Join-Path $PSScriptRoot "pyproject.toml"))) {
    $app = $PSScriptRoot
}
```

> ps2exe 会把 `$PSScriptRoot` 设为 exe 所在目录，所以两条分支在编译后等价；
> 差异只在「未编译直接跑脚本」时出现——而 §6 step 1 恰恰要求人手改这个文件，
> 所以这条分支一定会被踩到。
