# AntNest 架构讲解 · 面试简报

> 文中所有数字均为仓库实测（2026-10-12），被追问时可直接落到代码。

---

## 0. 三十秒电梯稿

> AntNest 是一个桌面级 AI Agent：蚁后（主模型）在窗口里干活，把子任务派给
> 一层工蚁（隔离子进程）并行执行，全程权限闸门、事件留痕、可回放。
> 它不依赖任何运行时框架——除 GUI 外全部标准库，2.7 万行 Python，644 个
> 测试 + 24 个离线评测全绿。核心卖点是三件事：**看得到**（每个决策可回放）、
> **管得住**（L0–L5 权限 + 作用域授权）、**会成长**（蚁后自撰工具、有记忆、
> 会反思，越用越强）。

---

## 1. 它是什么（非技术定位）

一句话：**一个在桌面上真实干活的 AI 员工，而不是一个聊天框。**

| | 聊天类 AI（ChatGPT 式） | AntNest |
|---|---|---|
| 形态 | 浏览器网页 | 原生 Windows 桌面应用 |
| 能力 | 生成文本 | 真正执行：读写文件、跑命令、派工蚁 |
| 可见性 | 黑盒 | 每步工具调用、权限判定、计划状态全部可见可回放 |
| 安全 | 平台侧限制 | 本地权限闸门，L0 只读到 L5 改自身源码逐级收紧 |
| 成长 | 无 | 自撰工具 + 记忆树 + 自我反思，跨会话沉淀 |

与同类开源项目的差异（README 已公开的口径）：
**OpenClaw 做"广度"**——网关接 29 个聊天渠道，人在手机上远程指挥；
**AntNest 做"深度"**——就在这台机器上当一个真实干活、看得见每一刀的代码工/系统工。

## 2. 架构总览

```
┌──────────────────────────────────────────────────────────────┐
│  桌面窗口 (pywebview, prototype_antnest.py ~14.5k 行)          │
│  聊天 · 计划 DAG · 工蚁轨迹 · 权限 · 技能表 · 回放             │
└───────────────┬──────────────────────────────────────────────┘
                │ app.update() / @app.route  (antnest_bridge)
┌───────────────▼──────────────────────────────────────────────┐
│  AntNestCore（Bridge）—— 惰性加载真实核心，UI 永不直接 import   │
├──────────────────────────────────────────────────────────────┤
│  蚁后主循环 antnest_loop                                       │
│   ① 权限闸门 check_permission ←── antnest_permissions L0–L5   │
│   ② 记忆注入 RAG ←── memory_tree(B+树) + memory_retrieval(BM25)│
│   ③ LLM 流式调用 ←── antnest_llm（OpenAI 兼容，任意端点）       │
│   ④ 工具派发 ←── antnest_registry.TOOL_SPECS（唯一真源）        │
│   ⑤ 计划派生 ←── antnest_plan（拒绝的 spawn 不留节点）          │
│   ⑥ 事件落盘 ←── antnest_events（JSONL，fail-open，脱敏）       │
│   ⑦ 检查点 ←── antnest_checkpoint（工具批次闭合时快照）          │
└──────┬───────────────────────────────────────────────────────┘
       │ spawn_clone
┌──────▼───────────────────────────────────────────────────────┐
│  工蚁（独立进程，隔离目录，只读环境变量拿策略）                  │
│  antnest_clone_worker —— 叶子模块：只许 import antnest_log+stdlib│
│  沙箱式隔离目录执行命令 / 写文件 → 结果回传蚁后                  │
└──────────────────────────────────────────────────────────────┘
```

### 模块分工（22 个核心模块，371 KB）

| 模块 | 职责 |
|---|---|
| `antnest_bridge` | UI ↔ 核心 桥；惰性加载；就绪状态管理 |
| `antnest_loop` | 蚁后主循环：权限→记忆→LLM→工具→事件→检查点 |
| `antnest_permissions` | L0–L5 权限模型、作用域授权、fail-closed |
| `antnest_registry` | 17 个工具的唯一硬编码清单，其余全部派生 |
| `antnest_events` | 事件日志（可回放）+ 审计日志（仅安全事件） |
| `antnest_plan` | 计划 DAG：环整体拒绝、变更在锁内 |
| `antnest_checkpoint` | 对话快照：静止点取、剥离思维链、数值排序 |
| `antnest_clone_worker` | 工蚁进程入口（叶子模块，见 §3.1） |
| `antnest_toolforge` | 蚁后自撰工具的登记/持久化/校验 |
| `memory_tree` / `memory_retrieval` | B+ 树记忆 + 零依赖 BM25 检索 |
| `antnest_inventory` | 从 import 图派生打包清单（防手写清单腐烂） |
| `antnest_config` / `antnest_config_schema` | 配置读写与 schema 校验 |

## 3. 七个关键设计决策（讲解的主菜）

> 每一条都是「遇到什么问题 → 否掉了什么方案 → 为什么这么定 → 用什么测试守着」。
> 面试官真正想听的不是功能列表，是这种**判断过程**。

### 3.1 叶子模块隔离 —— 一次 import 顺序引发的事故

**问题**：`antnest_config.py` 在第 25 行 import 工蚁模块，但此时它自己还没初始化完
（半初始化状态）。工蚁模块如果反手 import 任何依赖 config 的东西，就是**循环导入，
在 import 期直接杀死所有工蚁进程**。

**被否的方案**：延迟 import 到函数内——治标不治本，依赖闭包还是烂在里面，下次
有人加一行 import 就复发。

**决定**：把 `antnest_clone_worker` 定为**叶子模块**——只许 import `antnest_log`
和标准库，策略通过环境变量传入，工蚁侧永不 import 业务模块。

**守卫**：`WorkerLeafModuleTest` 静态扫描 import 传递闭包，引入任何传递依赖即失败。

**讲解要点**：这是一个典型的「用结构性约束消灭一整类 bug」的案例——不是修一次
import 错误，而是让这类错误在 CI 里不可能再出现。

### 3.2 权限闸门的两个不可让步顺序

权限有 L0（只读审阅）到 L5（改自身源码）六级。**两条顺序是语义，写错就是安全洞**：

1. **人工确认判定必须排在等级判定之前**。反过来，level=5 时 `SELF_MOD(5) <= 5`
   直接放行——「改自身源码永远需要人确认」这个不变量就被绕过了。
2. **参数敏感判定覆盖静态等级**。`write_file` 静态是 L1（低危），但路径指向
   核心源码时必须升级为「人工确认」。静态等级管工具，参数判定管这一次调用。

再加两条：**未知工具一律 fail-closed 拒绝**（漏登记的新工具不会静默放行）；
**授权按作用域签发**（`write:<路径>`、`cmd:<命令>`）——批准改一个文件不等于
批准改整个仓库。

**守卫**：`tests/test_permissions.py` + `test_permission_gate.py`，
端到端真跑一遍主循环（mock LLM，不联网）。

**讲解要点**：能主动讲出「顺序即语义」这种点，说明不是 CRUD 思维，是真正
设计过有安全含义的系统。

### 3.3 单一真源注册表 —— 对抗"清单腐烂"

17 个工具的元数据只在 `TOOL_SPECS` 一处硬编码。执行器映射、暴露给 LLM 的
schema 列表、畸形调用检测正则、prompt 里的工具清单，**全部从它派生**。

**为什么**：多处手写同一份清单必然腐烂（此前就有死 CSS 类、prompt 与注册表
不一致的真实案例）。新增工具只改两处（TOOL_SPECS + schema），任何地方都不许
手写工具名枚举。

**守卫**：`tests/test_registry.py`；prompt 清单一致性由 `QueenPromptFileTest`
卡住；打包清单由 `PackagingManifestTest` 对 import 图派生结果做 diff。

### 3.4 检查点必须在"静止点"取

对话可能被压缩/恢复。朴素做法「保留最后 N 条消息」会产生**被 API 直接拒绝的
列表**：切点落在工具批次中间，列表以 `role:"tool"` 开头；system prompt（含全部
安全规则）整个丢失；思维链字段被明文持久化。

**决定**：快照只在**工具批次闭合的静止点**取（主循环 while 顶部），
**永远不从工具内部调**——那时 messages 正在被追加，快照是撕裂的。
落盘前剥离思维链字段；列表按数值排序而非文件名字符串序（seq 过千后字符串序会错）。

**讲解要点**：这是和「数据库事务要在一致状态点做快照」同源的思想，面试官一听
就知道懂并发。

### 3.5 事件日志的三条铁律

1. **fail-open 但首次失败必须打 WARNING**——否则「静默丢弃」和「正常无记录」
   无法区分，等于没有日志。
2. **绝不落盘推理内容和凭据**——`reasoning_content`、`api_key` 一律脱敏，
   token 指标白名单放行。
3. **落在项目目录而非安装目录**——安装版的应用目录只读，写在那里记录会被
   静默丢弃。

`events/*.jsonl` 可回放（给人看 + 可机读），`audit.log` 只记安全事件。
**不双写**——双写是未来不一致的来源。

### 3.6 「计划不许说谎」—— 被拒绝的 spawn 不留节点

计划 DAG 有两个数据源（LLM 显式规划 + spawn 自动派生）。规则：**权限闸门
必须排在计划派生之前**。反过来的话，被拒绝的 spawn 也会在计划里留下节点——
但那件事根本没发生，**计划就在说谎**。

同样的语义洁癖：检测到环时**整体拒绝**并保留原计划——半个新计划比旧计划更糟
（引入半个新计划 = 状态既不是 A 也不是 B，无法回滚）。

### 3.7 检索为什么不用向量模型 —— 一个量级判断

蚁后的记忆检索用的是**106 行纯标准库 BM25**，不是 embedding。

**理由**：
- 查询和记忆里全是**代码标识符**（函数名、文件路径、报错串）——这类稀有
  token 恰是 embedding 的已知弱点（低词频→向量估不准），而 BM25 的 IDF
  对稀有词给最高权重。**在这个场景 BM25 不是妥协，是更准。**
- 可解释：能说清命中了哪段哪个词；向量说不清。
- 零依赖（本项目的硬约束，见 §5）、无需 GPU、记忆文件保持人可读的 JSON/Markdown。
- 量级：记忆在几百到几千段落，BM25 的舒适区。向量模型的优势要到十万段落以上。

**已知的盲区和补法**：无词重叠的语义召回（问"为什么崩"而记忆里写"空指针"）
用 **BM25 粗召回 + LLM 重排**补——不引入向量模型，语义能力由本来就有的 LLM
提供，且天然降级（无 key 时跳过重排直接用 BM25 top-k）。

**讲解要点**：这是「按场景选技术而不是按流行度选技术」的最好例证。

## 4. 质量体系（这段最能加分）

| 机制 | 做法 |
|---|---|
| 测试 | **644 个测试 + 38 个子测试**全绿，~26 秒跑完 |
| 离线评测 | **24/24 通过（100%）**，不联网——mock LLM 测的是运行时管线行为 |
| 变异测试 | **故意破坏代码，确认守卫测试会失败，再还原**。技能表上线时对 5 道护栏逐一做了变异验证 |
| 发布预检 | `tools/release_check.ps1` 一键：清单一致性、依赖、安装产物 |
| 守卫覆盖 | 每条硬约束都有对应测试：叶子模块、清单派生、权限顺序、事件铁律、计划语义、检查点静止点 |

**最近的真实案例（讲这个非常加分）**：技能表上线后用户启动即崩——
`bridge.Bridge()` 这个类根本不存在。644 个测试全绿却没抓到，为什么？
根因：**没有任何测试 import 那个 14k 行的 GUI 模块**（一 import 就启动窗口），
语法检查抓不了属性名错误。修复不只改一行代码：加了一个**静态 AST 护栏**，
扫描全部 `bridge.X` 引用断言真实存在，并用变异测试验证护栏真的抓得住。
**从"炸了再修"变成"这类错误永远进不了 CI"。**

## 6. 诚实边界（主动讲，比被问出来强十倍）

1. **工具派发目前是串行的**。工蚁是独立进程（真隔离），但主循环里
   `for tc in tool_calls` 逐个执行。并行的方案已经想清楚
   （`concurrent.futures` + `tool_call_id` 原序回填 + 事件时序保证），
   这是路线图第一项。
2. **权限闸门不是沙箱**。拦截靠规则与等级判定，`python x.py` 里藏的
   `rmtree` 拦不到。真隔离靠工蚁的进程/目录隔离。文档和 UI 措辞从不夸大。
3. **两个已知技术债**：共享可变全局 + 延迟访问的双命名空间（历史上造成过
   每次工具调用抛 AttributeError 的 bug）；GUI 主文件 14k 行单文件
   （用"纯渲染函数拆到独立模块 + 静态护栏"缓解，根治待拆）。
4. **Windows-only**。跨平台成本高于当前单人项目的收益，明确不做优先级。

**为什么主动讲**：面试官对"项目毫无缺点"的叙述是免疫的。能精确说出
"哪里没做好、为什么暂时不做、计划怎么解"，反而是区分度最高的信号。

## 7. 可能被问到的问题 · 答法要点

**Q: 为什么不用 LangChain / AutoGPT 框架？**
A: 框架的抽象层会挡住三样我要的东西：权限闸门要插在工具派发的**精确位置**
（顺序即语义）；事件要按我的铁律落盘；零依赖约束下框架的依赖树不可接受。
框架适合快速出 demo，我要的是每一行都可审计的执行层。

**Q: 最大的技术挑战是什么？**
A: import 期循环导入杀死工蚁（§3.1）。难点不在修，在**意识到这必须用结构性
约束消灭**而不是修一次了事——以及把约束做成会自己腐烂报警的测试。

**Q: 怎么保证 AI 不会干危险的事？**
A: 分层：权限闸门（L0–L5 + 作用域授权 + fail-closed）管"能不能做"；
工蚁进程隔离 + 隔离目录管"做了影响多大"；事件审计管"做了什么可以查"。
并且诚实：闸门不是沙箱，正则提示拦不住藏起来的危险调用，所以最高危操作
（L4/L5）一律人工确认。

**Q: "越用越好用"具体指什么？**
A: 三个已实现的机制：自撰工具（蚁后把重复劳动固化成自己的新工具，登记时
合并旧元数据防覆盖丢名）；记忆树（episodic→knowledge 分层 + BM25 检索注入）；
自我反思沉淀为持久知识。界面用技能表把成长可见化——内置能力 12 项、
自撰工具计数常驻显示。

**Q: 下一步做什么？**
A: 优先级明确：① 工具真并行（唯一"承诺了没兑现"的点，方案已定）；
② 自撰工具的语法/可加载校验（现在登记时不查语法，登记成功≠能跑）；
③ 经验库——把事件日志从"可回放"升级为"可检索"，失败轨迹自动提炼、
下次注入规避。第 ③ 点对应"记忆权重调度"的思路：管理何时想起、想起多少、
哪些必须压住，而不只是"检索最相关的 K 条"。

**Q: 为什么单文件 GUI 14k 行？**
A: 诚实回答：演化产物，是最大的债。缓解措施已落地（纯渲染函数拆到
`ui_render.py` 独立可测、AST 静态护栏补 import 盲区），根治方案是按
面板拆模块，排在大重构窗口做。

## 8. 讲解路线建议

**3 分钟版**：电梯稿 → 架构图指一遍（蚁后循环 7 步 + 工蚁隔离）→
数字速览表 → 主动讲一个设计决策（推荐 §3.2 权限顺序，或 §3.1 import 事故）→
主动讲诚实边界第一条 + 热修案例（§4）。

**10 分钟版**：以上全部 + 七个决策逐条过 + 质量体系完整讲 + Q&A 里的
"为什么不用框架/向量"两个判断题。

**一条铁律**：每个功能主张都落到"问题→被否方案→决定→守卫测试"的叙事。
功能谁都有，**判断过程才是面试的差异化**。
